# Payroll banking — Batch 2

This cumulative delivery integrates company funding profiles with payroll payment batches. It includes the previous company banking foundation and service/menu changes.

## Install
Preserve API .env and UI .env.local. Back up the database, apply both packages, then in the API folder run:

```bash
npm ci
npx prisma migrate deploy
npx prisma generate
npm run build
npm run start:dev
```

This adds migration `20260930140000_payroll_payment_freeze`: nullable funding snapshot/profile reference, frozen payment date, export format/content type/checksum and file bytes on PayrollPaymentBatch. Existing rows are not retroactively assigned new funding details. The previous company-banking migration is included too. In the UI folder run `npm ci && npm run build`, then `npm run dev -- --port 3001`.

## What works
- Payroll cycle and payment modules are now registered in AppModule. Their controllers require organization-scoped permissions, not SELF or TEAM grants. Payroll feature/tenant guards remain active.
- Payroll & Payments → Payment Batches lists existing payment batches and provides selectors for locked payroll cycles and approved same-company funding profiles.
- Preparation uses an explicit approved funding profile or the approved SALARIES default. It freezes the account, branch, bank/channel/adapter/version, payment date, employee identity and references alongside existing beneficiary snapshots and amounts. Profile/default changes do not alter that batch. Preparation without a default/override remains report-only.
- A different authorized user must approve release. The page shows masked frozen funding and employee beneficiary details, amounts and references. The original independent funding-account approval remains a separate check in Banking & Payments.
- Generic CSV reports have a dedicated audited download endpoint and do not change payment status. Production generation rejects the generic report adapter. This corrects the older behavior where generic CSV generation could advance a batch to EXPORTED.
- The production export pipeline stores the original bytes, SHA-256, format, filename, content type and export reference transactionally when a future verified adapter succeeds. Repeat requests return those stored bytes after checksum validation and audit; format switching and cancelled downloads are rejected. Concurrent exports request a retry rather than returning newly regenerated bytes.
- An already EXPORTED legacy batch without saved bytes cannot be regenerated through the production export endpoint; recover its original file instead. Legacy report views may use old live identity/date fallbacks because existing snapshots lack those fields. New batches freeze them.

## FNB draft and current bank limitations
FNB Enterprise Bankserv version 2023-02 has a draft serializer: fixed field positions, integer cents, standard/extended recipient account slots, sequencing, action date and header/contra/trailer records. It validates supported accounts, currencies, positive two-decimal amounts, totals/counts, unique references and strict field widths; it rejects overlong names/references instead of silently truncating them.

The official PDF calls the full record length 181 characters including CR/LF, while its field tables reach position 180. The draft uses 180 data characters plus CRLF and is therefore NOT bank-verified. Its filename starts DRAFT-NOT-FOR-BANK-UPLOAD. It does not implement profile-dependent hash verification; its trailer hash area is blank. These choices require bank confirmation before production release. No bank import or live transfer was tested.

Official specification: https://www.online.fnb.co.za/rhelp_0_15/OBE_SA_Downloads/assets/docs/Payment_Bankserv_File_Format_SA.pdf

Choose an independently approved FNB_OBE_BANKSERV funding profile before preparing a batch to use this draft. After independent release approval, Validate FNB draft shows blocking issues and the bank-validation warning; Download FNB draft records an audit only. It neither sets EXPORTED nor allows a bank submission based on the draft. Do not upload it for payments.

All production bank adapters remain unavailable. FNB CSV/XML and Standard Bank mapped Excel still require full implementation/test evidence; other formats still require complete specifications. Existing bank-submission/result routes are retained for eligible previously exported batches; this delivery creates no bank-ready export or new automatic payment. Early Pay platform treasury, actual payouts, employer settlement files and statutory remittance configuration remain later batches.

## New/changed API contracts
- POST /payroll-payments/batches/:payrollBatchId/prepare accepts optional `{fundingProfileId}`; omit it to use the salary default or legacy report-only preparation.
- GET /payroll-payments/funding-profiles returns only approved same-company funding choices with masked accounts; requires PREPARE_PAYROLL_PAYMENTS.
- POST /payroll-payments/batches/:id/report downloads generic CSV without a payment-state transition.
- POST /payroll-payments/batches/:id/draft/FNB_OBE_BANKSERV downloads the draft only after release approval and layout validation.
- GET /payroll-payments/batches/:id includes masked frozen funding/beneficiaries and checksum metadata, never full snapshots or stored export bytes.
- Existing production export endpoints accept only a bank-importable AVAILABLE adapter matching the frozen funding profile. None currently qualifies. Downloads remain authenticated and private/no-store.
